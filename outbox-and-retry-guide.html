Do not lose events when Redis is down

A step-by-step guide to the outbox pattern and retry, written for the code you already have in app/events.py.

What is going wrong today

When you create a task, create_task saves it in Postgres, then calls publish_event. That function sends the event to a Redis Stream. Here is the important part of it:

app/events.py (current)
try:
    redis_client.xadd(settings.EVENT_STREAM, {...})
except RedisError:
    # the event is gone forever. Nobody will try again.
    logger.warning("Redis unavailable, %s event not published", event_type)

So there are two ways to lose an event:

  • Redis is down. The task is saved, the warning is logged, and the event disappears.
  • The app crashes after session.commit() but before publish_event runs. The task exists, the event never does.

The comment in your file already says it: "no outbox or retry". Let's add both.

The idea in a shop story

You run a small shop. After each sale you must call the delivery company. Sometimes their phone is busy.

Bad way: make the call right away. If it is busy, you forget about it. The parcel never ships.

Good way:

  1. At the moment of the sale, write the delivery note in your notebook. Same pen, same moment, so the sale and the note can never be separated.
  2. A helper reads the notebook and calls the delivery company.
  3. If the phone is busy, the helper waits a bit and calls again. First 2 minutes, then 4, then 8.
  4. When the call works, the helper ticks the note as done.
Pattern 1

Outbox = the notebook

A table in your own database. When you save a task, you also save an "event to send" row in the same transaction. If the task is saved, the event row is saved. Always both, or neither.

Pattern 2

Retry = call again later

A background helper (the relay) reads pending rows and sends them to Redis. If Redis fails, it waits longer each time and tries again. Nothing is deleted until the send works.

The new flow

1. API requestPOST /tasks
→
2. One committask row + outbox row in Postgres
→
3. Relaybackground loop, every 2 seconds
→
4. Redis StreamXADD, then mark row "sent"

The request never talks to Redis any more. It only talks to Postgres, which you already trust. If Redis is down, the rows just wait in the table until Redis comes back.

How long does the relay wait between tries?

Each failure doubles the wait, up to a limit of 60 seconds. This is called exponential backoff. It stops you from hammering a Redis that is already struggling.

Failed tries123456+
Wait before next try2s4s8s16s32s60s

Formula used in the code: min(2 ** attempts, 60) seconds.

Apply it in your code

Six small steps. Each one shows the file to change. Lines on a green background are new; lines on a red background are removed.

Step 1. Add the outbox table model

New file. It is the "notebook". Each row is one event waiting to be sent.

app/models/outbox.py (new)
from datetime import datetime
from typing import Any

from sqlalchemy import JSON, Column, DateTime
from sqlmodel import Field

from .base import BaseTable, current_time

PENDING = "pending"
SENT = "sent"
DEAD = "dead"  # gave up after too many tries; needs a human


class OutboxEvent(BaseTable, table=True):
    __tablename__ = "outbox_event"

    event_type: str
    payload: dict[str, Any] = Field(sa_column=Column(JSON, nullable=False))
    status: str = Field(default=PENDING, index=True)
    attempts: int = 0
    last_error: str | None = None
    next_attempt_at: datetime = Field(
        default_factory=current_time, sa_type=DateTime(timezone=True)
    )
    sent_at: datetime | None = Field(default=None, sa_type=DateTime(timezone=True))

Step 2. Add three settings

app/config.py
    REDIS_TIMEOUT: float = 1.0
    OUTBOX_POLL_SECONDS: float = 2.0     # how often the relay looks at the table

Step 3. Change events.py: write to the table, do not call Redis

add_to_outbox only adds a row to the session. It does not commit. The caller commits, so the task and the event go in together. The event_id is created here, once, so every retry sends the same id.

app/events.py
from datetime import datetime, timezone
from typing import Any
from uuid import uuid4

import json
import logging
from redis import RedisError
from app.cache import redis_client
from app.config import settings
from sqlmodel import Session
from app.models.outbox import OutboxEvent

EVENT_SOURCE = "task-manager-api"


def add_to_outbox(session: Session, event_type: str, data: dict[str, Any]) -> None:
    event = {
        "event_id": str(uuid4()),
        "event_type": event_type,
        "occurred_at": datetime.now(timezone.utc).isoformat(),
        "source": EVENT_SOURCE,
        "data": data,
    }
    session.add(OutboxEvent(event_type=event_type, payload=event))  # no commit here

The old publish_event function goes away. Its xadd call moves into the relay (step 4).

Step 4. Write the relay with retry

New file. relay_once() picks pending rows that are due, sends each to Redis, and either marks them sent or schedules the next try.

app/outbox.py (new)
import json
import logging
import threading
from datetime import timedelta

from redis import RedisError
from sqlmodel import Session, select

from app.cache import redis_client
from app.config import settings
from app.database import engine
from app.models.base import current_time
from app.models.outbox import DEAD, PENDING, SENT, OutboxEvent

logger = logging.getLogger(__name__)


def backoff_seconds(attempts: int) -> int:
    return min(2 ** attempts, 60)  # 2, 4, 8, 16, 32, 60, 60 ...


def relay_once() -> int:
    """Send due events to Redis. Returns how many were sent."""
    sent = 0
    with Session(engine) as session:
        rows = session.exec(
            select(OutboxEvent)
            .where(OutboxEvent.status == PENDING)
            .where(OutboxEvent.next_attempt_at <= current_time())
            .order_by(OutboxEvent.created_at)
            .limit(settings.OUTBOX_BATCH_SIZE)
            .with_for_update(skip_locked=True)  # two workers never take the same row
        ).all()

        for row in rows:
            try:
                redis_client.xadd(
                    settings.EVENT_STREAM,
                    {"event_type": row.event_type, "payload": json.dumps(row.payload)},
                    maxlen=settings.EVENT_STREAM_MAXLEN,
                    approximate=True,
                )
            except RedisError as exc:
                row.attempts += 1
                row.last_error = str(exc)[:500]
                if row.attempts >= settings.OUTBOX_MAX_ATTEMPTS:
                    row.status = DEAD
                    logger.error("Outbox event %s is dead: %s", row.id, exc)
                else:
                    row.next_attempt_at = current_time() + timedelta(
                        seconds=backoff_seconds(row.attempts)
                    )
                session.add(row)
                break  # Redis is down: stop here, do not hammer it with the rest

            row.status = SENT
            row.sent_at = current_time()
            session.add(row)
            sent += 1

        session.commit()  # one commit per batch keeps the row locks until the end
    return sent


def run_relay(stop: threading.Event) -> None:
    while not stop.wait(settings.OUTBOX_POLL_SECONDS):
        try:
            relay_once()
        except Exception:
            logger.exception("Outbox relay crashed, will try again")

Step 5. Start the relay with the app

FastAPI's lifespan runs code on start and on stop. We start the loop in a background thread there.

app/main.py
import threading
from contextlib import asynccontextmanager
import logging
...
from app.outbox import run_relay

@asynccontextmanager
async def lifespan(app: FastAPI):
    stop = threading.Event()
    thread = threading.Thread(target=run_relay, args=(stop,), daemon=True)
    thread.start()
    yield
    stop.set()
    thread.join(timeout=5)

app = FastAPI(title="Task Manager API")
app = FastAPI(title="Task Manager API", lifespan=lifespan)

Step 6. Use the outbox inside create_task

Two small changes: add the outbox row before the commit, and drop the old direct call. flush() sends the task to the database without committing, so we can use its data.

app/routers/tasks.py
from app.events import publish_event
from app.events import add_to_outbox
...
def create_task(task_data: TaskCreate, session: SessionDep):
    task = Task.model_validate(task_data)

    session.add(task)
    session.flush()
    add_to_outbox(
        session, "task.created", TaskRead.model_validate(task).model_dump(mode="json")
    )
    session.commit()          # task and event are saved together
    session.refresh(task)
    cache_invalidate(LIST_KEY)
    publish_event("task.created", TaskRead.model_validate(task).model_dump(mode="json"))

    return ok(task, "Task created")

Test it with a real Redis outage

Your Compose file already has everything you need. The API runs on port 8010.

terminal
# 1. Stop Redis
docker compose pause redis

# 2. Create a task. It should still return 201.
curl -X POST localhost:8010/tasks -H "Content-Type: application/json" \
  -d '{"title": "Buy milk"}'

# 3. The event waits in Postgres, with attempts going up
docker compose exec db psql -U postgres -d tasks \
  -c "select event_type, status, attempts, next_attempt_at from outbox_event;"

# 4. Bring Redis back
docker compose unpause redis

# 5. Wait about a minute. The row turns "sent" and the stream has the event.
docker compose exec redis redis-cli XRANGE events:tasks - +

If step 5 shows your task.created event, it works. Before the change, that stream would have been empty.

Things you should know

  • Duplicates can happen. If Redis saved the event but the reply got lost, the relay sends it again. This is called at-least-once delivery. Every event has a fixed event_id, so whoever reads the stream should ignore ids it has already seen.
  • Events arrive a little later. Up to 2 seconds in normal times, since the relay checks on a timer. That is the price for never losing them.
  • "Dead" rows need a human. After 20 failed tries a row becomes dead and an error is logged. Watch for them with select * from outbox_event where status = 'dead'. After fixing Redis, set them back to pending to retry.
  • Several app workers are fine. skip_locked makes each worker take different rows.
  • The table grows. Plan to delete old sent rows now and then, for example anything older than 7 days.
  • Only create publishes an event today. Update and delete do not. When you want task.updated or task.deleted, call add_to_outbox before their commit in the same way.
  • The cache is different. Cache failures are fine to ignore, because the database is the real source. Events are not fine to ignore, which is why only events get an outbox.

Cheat sheet

Outbox

Save the event in your database, in the same commit as the data. Never call Redis from the request.

Relay

A loop that reads pending rows and sends them to Redis. Marks them sent only after success.

Retry

On failure, wait min(2 ** attempts, 60) seconds and try again. Stop after a maximum and mark dead.

Idempotency

Same event_id on every retry, so readers can skip duplicates.
